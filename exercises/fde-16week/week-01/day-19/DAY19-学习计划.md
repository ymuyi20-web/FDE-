# Day 19 学习计划：版本迭代计划与变更记录

## 今日主题

把 Day18 收到的反馈，变成下一版产品的修改计划。

FDE 不是“谁提意见就马上改”，而是把反馈整理成版本：这一版改什么、不改什么、为什么、怎么验收、发给谁复测。

## 今日目标

- 学会用版本号管理原型；
- 把反馈分成“本版处理”和“暂缓处理”；
- 为每条改动写验收标准；
- 生成一份可交付的 release note；
- 理解版本计划在 FDE 项目里的作用。

## 今日文件

- `release_planner.html`：版本迭代计划器；
- `CHANGELOG_DRAFT.md`：变更记录模板；
- `DAY19-学习计划.md`：今天的学习说明。

## 关键概念

### 1. 反馈不是版本

反馈只是原始材料。

版本计划要回答：

- 这一版解决哪些问题；
- 哪些问题不解决；
- 为什么这样排序；
- 改完后怎么确认真的好了。

### 2. 版本号表达交付状态

建议用简单规则：

- `v0.1`：能跑的原型；
- `v0.2`：根据第一轮反馈修正；
- `v0.3`：给第二批用户试用；
- `v1.0`：经过核心场景验证，可以正式作为小工具交付。

### 3. 验收标准比“我改了”重要

不要只写“优化地区分类”。

要写：

“水稻地区下拉框能看到长江中下游、东北、华南、西南、其他；旧记录仍能正常生成方案。”

这才是可验收的交付。

## 今日练习

1. 打开 `release_planner.html`；
2. 点击“填入 Day17 示例计划”；
3. 查看本版改动、暂缓项和验收清单；
4. 生成 release note；
5. 自己再添加一条新需求，并判断是否放入当前版本。

## 今日复盘问题

1. 为什么一个版本里不能塞太多需求？
2. “已修改”和“已验收”有什么区别？
3. 为什么 release note 要写“不做什么”？
4. 如果朋友反馈“再加一个智能推荐”，你会直接放进当前版本吗？为什么？

## 今日交付标准

- 能打开版本计划器；
- 能新增、删除迭代项；
- 能区分本版处理和暂缓处理；
- 能生成 release note；
- 能说清楚一个版本的 Echo 和 Delta。
