> 把“帮我整理一个农业成本计算工具”转化为清楚的用户、输入、输出、边界和验收标准。

- 分清确定性计算与必须人工确认的农业业务判断；
- 写出一张可以交给开发者或 Agent 执行的 issue。

## 第一阶段：理解 GitHub 协作语言（30 分钟）

阅读：

- [GitHub Hello World](https://docs.github.com/zh/get-started/start-your-journey/hello-world)
- [GitHub Issues 简介](https://docs.github.com/zh/issues/tracking-your-work-with-issues/learning-about-issues/about-issues)

只掌握以下对应关系，不背命令：

| 词汇 | 通俗理解 | FDE 场景 |
|---|---|---|
| repo | 项目的完整档案 | 代码、数据样例、说明、历史都放在一起 |
| issue | 可追踪的需求单 | 把业务人员的模糊要求写成验收项 |
| commit | 一次有意义的存档 | 记录“改了什么、为什么改” |
| branch | 不影响正式版本的平行草稿 | 在独立空间修改和试错 |
| PR | “改好了，请审核” | 带着改动说明和测试证据提交交付 |
| review | 审核 | 判断是否满足业务边界和验收标准 |
| merge | 接受改动进入正式版本 | 审核通过后成为当前有效版本 |

今天最重要的两句话：

- `issue` 是 Echo 的落点：把现场语言变成可追踪任务。
- `PR` 是 Delta 的交付单元：把实现和证据交给别人审核。

## 第二阶段：阅读现有代码（35 分钟）

打开 `day01_cost_calculator.py`，按以下顺序阅读：

1. 找到输入数据来自哪里；
2. 找到面积是在哪里取得的；
3. 找到每亩成本如何计算；
4. 找到总成本如何计算；
5. 找到结果如何输出；
6. 找到异常在哪里被处理。

不要先改代码。先在纸上画：

```text
JSON 农资数据 + 用户输入面积
            ↓
     检查数据是否合法
            ↓
    计算每亩成本和总成本
            ↓
          屏幕输出
```

## 第三阶段：运行与观察（30 分钟）

在本目录运行：

```powershell
python .\day01_cost_calculator.py
```

依次测试：

1. 输入 `100`；
2. 输入 `0`；
3. 输入 `-10`；
4. 输入 `abc`；
5. 把 JSON 中某个 `cost_per_mu` 临时改为负数，观察提示，再改回来。

把每组测试的“输入、预期、实际结果”记录到学习笔记。

## 第四阶段：填写项目契约（30 分钟）

打开 `PROJECT_CONTRACT.md`，重点检查：

- 用户是否具体；
- 输入是否有字段和单位；
- 输出是否能被验证；
- 哪些内容必须人工确认；
- 哪些功能本周明确不做。

这一步是 FDE 的 Echo 能力。真正困难的不是把数字乘起来，而是把边界说清楚。

## 第五阶段：完成 issue 草稿（20 分钟）

打开 `ISSUE_DRAFT.md`，用你自己的语言修改，不要原样照搬。

一张合格 issue 必须让另一个人只看文字就知道：

- 为什么做；
- 做给谁；
- 要改什么；
- 不改什么；
- 完成后怎么验收。

## 第六阶段：复盘（15 分钟）

在学习笔记中回答：

1. 为什么成本数字不应该交给大模型生成？
2. “能运行”与“可交付”有什么区别？
3. 如果肥料价格来自去年的表格，程序算对了是否等于业务结果正确？
4. 今天这张 issue 中，哪些属于 Echo，哪些将来属于 Delta？

参考答案方向：

- 模型输出具有不确定性，金额计算应由确定性代码完成；
- 可交付还要求别人能运行、理解、验证并知道边界；
- 程序正确不等于数据正确，价格时效性必须由业务人员确认；
- 问题定义和验收标准属于 Echo，实现、测试和交付属于 Delta。
