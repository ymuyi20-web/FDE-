# 第 01 周执行手册：接上现有代码，建立交付习惯

## 本周定位

这是新版 16 周路线中的第 1 周，不是重新学习 Python 变量、循环和函数。

你已经完成了成本计算、JSON 配置、CSV 历史记录和菜单程序。本周要做的是把这些零散练习收束成一个别人能够运行、检查和验收的小型交付物。

FDE 对应关系：

- `issue`：把现场提出的模糊问题变成可验收任务；
- `branch`：在不影响稳定版本的前提下修改；
- `commit`：留下每一步改动的审计记录；
- `PR`：提交一份带证据的“请审核”交付单；
- `test`：证明确定性计算没有被改坏；
- `README`：让用户不依赖作者也能运行和判断适用边界。

## 本周结果

完成一个“水稻农资成本计算器 v1.0”仓库，至少包含：

```text
farm-cost-calculator/
├─ src/
│  └─ farm_cost.py
├─ data/
│  └─ farm_inputs.example.json
├─ tests/
│  └─ test_farm_cost.py
├─ docs/
│  └─ demo-record.md
├─ README.md
├─ .gitignore
└─ requirements.txt
```

最终验收：

- 新用户按照 README 能在 10 分钟内运行；
- 有至少 5 次含义清楚的提交；
- 有 1 个写清验收标准的 issue；
- 有 1 个从独立分支提交的 PR；
- 10 条自动化测试全部通过；
- 能在 5 分钟内说明输入、计算、输出、异常和限制；
- 不包含真实业务敏感数据、密码或 API 密钥。

## Day 1：冻结项目边界

### 学习内容

- FDE 交付不是“功能越多越好”，而是输入、输出、边界和验收清楚。
- 理解 repo、issue、commit、branch、PR、review、merge 的业务含义。
- 学会把“把以前的练习整理一下”改写成可验收 issue。

### 实操

1. 以 `day11_project_manager.py` 为主干，参考 `day12_config_manager_v2.py` 的配置管理能力。
2. 暂时不加入 AI、网页、数据库或施肥推荐。
3. 写一张项目契约：

| 项目 | 本周定义 |
|---|---|
| 用户 | 需要快速核算水稻农资投入的农业生产管理人员 |
| 输入 | 面积、农资名称、各农资亩成本 |
| 确定性输出 | 每亩成本、总成本 |
| 辅助输出 | CSV 历史记录或文本报告 |
| 人工边界 | 数据真实性、农资是否适用、价格是否有效由人确认 |
| 明确不做 | AI 建议、作物模型、施肥处方、在线部署 |

4. 创建 issue：《整理水稻农资成本计算器 v1.0》。
5. issue 必须写：背景、用户、范围、明确不做、验收标准。

### 当天验收

- 能用一分钟说清“为谁解决什么问题”；
- issue 中至少有 5 条可以打勾的验收项；
- 没有把“学习 Git/Python”写成项目目标。

## Day 2：把代码放进可协作的仓库

### 学习内容

- repo 是项目完整档案，不只是代码文件夹；
- commit 是一次有明确含义的存档；
- branch 是不改动稳定版本的平行草稿；
- issue 是需求台账，PR 是交付与验收单。

### 实操

1. 创建仓库和目录骨架。
2. 只复制本项目真正需要的代码，不把 Day 1–12 所有练习一股脑放进去。
3. 增加 `.gitignore`，排除缓存、虚拟环境和临时输出。
4. 完成两次提交：
   - `chore: 建立成本计算器项目结构`
   - `docs: 添加项目范围和验收标准`
5. 在提交历史中检查每一次改动是否对应一个明确目的。

### 当天验收

- 能指出仓库、提交历史和当前分支；
- 两次提交没有混入无关图片或练习文件；
- 能解释为什么“把所有改动一次提交”不利于审核。

## Day 3：整理确定性计算核心

### 学习内容

- 计算逻辑与键盘输入、打印、文件写入分离；
- 函数应具有明确参数、返回值和失败方式；
- 金额计算不能交给大模型猜测。

### 实操

把现有程序整理成至少三个独立职责：

1. `validate_inputs(area, items)`：检查面积和农资字段；
2. `calculate_cost_per_mu(items)`：计算每亩成本；
3. `calculate_total_cost(area, cost_per_mu)`：计算总成本。

同时保留一个最小运行入口，读取 `farm_inputs.example.json` 并显示结果。

建议先明确以下规则：

- 面积必须大于 0；
- 农资成本必须为数字且不得小于 0；
- 缺少必填字段时必须明确报错；
- 空农资列表可以返回 0，但必须在 README 中说明；
- 中文 JSON 使用 UTF-8。

### 当天验收

- 计算函数中没有 `input()`；
- 换一份 JSON 数据不需要修改计算函数；
- 错误数据不会被静默忽略；
- 完成一次只包含核心整理的提交。

## Day 4：用 10 条测试建立交付证据

### 学习内容

- 测试不是证明“程序永远正确”，而是冻结当前承诺；
- 每条测试应包含输入、预期结果和明确名称；
- `pytest` 会自动发现以 `test_` 命名的测试。

### 必做测试

1. 单个农资的每亩成本；
2. 多个农资的每亩成本；
3. 小数金额的计算；
4. 成本为 0 的合法项目；
5. 空农资列表；
6. 缺少 `cost_per_mu` 字段；
7. 成本为非数字文本；
8. 成本为负数；
9. 面积为 0；
10. 面积为负数。

对于小数比较使用 `pytest.approx()`，不要直接依赖浮点数完全相等。

### 当天验收

- 运行测试时显示 `10 passed`；
- 故意改错一个计算公式，至少一条测试会失败；
- 恢复公式后测试重新通过；
- 保存一次失败截图或文字记录作为证据。

## Day 5：写一份陌生人能使用的 README

### 学习内容

README 的目标不是记录“我今天学了什么”，而是降低交付和接手成本。

### README 必含内容

1. 项目解决什么问题；
2. 适用用户与场景；
3. 当前版本做什么；
4. 明确不做什么；
5. 输入字段和单位；
6. 运行前准备；
7. 运行方法；
8. 样例输入与输出；
9. 测试运行方法；
10. 已知限制和人工审核点。

增加一句农业安全边界：

> 本项目仅进行成本核算，不构成施肥处方或农艺建议；输入价格、产品适用性和田间执行条件必须由业务人员确认。

### 当天验收

- 把项目当作第一次看到，只按照 README 从头运行一次；
- README 中没有依赖“运行我电脑上的某个绝对路径”；
- 输入、输出都带单位；
- 至少记录一个已知限制。

## Day 6：完成第一次 PR 和自我审核

### 学习内容

- PR 不是上传代码，而是一次结构化的“请过目”；
- diff 是验收单：绿行是新增，红行是删除；
- review 要检查需求、正确性、风险和证据。

### 实操

1. 从主分支创建功能分支；
2. 在分支上补充一项小改动，例如“缺字段时报出具体字段名”；
3. 提交并创建 PR；
4. PR 描述使用以下结构：

```text
解决的问题：
本次改动：
明确未改：
验证方法：
测试结果：
风险与回滚：
关联 issue：
```

5. 在 Files changed 中逐文件检查；
6. 至少留下两条自我审核记录：一条关于业务边界，一条关于代码或测试；
7. 确认验收项后再合并。

### 当天验收

- PR 能关联 Day 1 的 issue；
- PR 中有测试结果；
- 能说明 diff 中每个文件为什么要改；
- 合并前完成一次明确的 review。

## Day 7：让交付面对一个“陌生用户”

### 实操

请朋友按 README 运行；如果暂时找不到朋友，就开启一个全新对话，让 AI 只阅读 README，不提供口头补充。

记录：

- 对方在哪一步卡住；
- 对哪个字段或单位理解错误；
- 是否能得到预期结果；
- 是否知道这个工具不能做施肥推荐；
- 需要修改的前三项。

修复高优先级问题后，为 v1.0 写周复盘：

```text
本周完成：
用户能完成的任务：
测试证据：
最容易出错的地方：
我仍不能独立解释的部分：
下周数据审计前必须补的事项：
```

### 当天验收

- 新用户不依赖作者解释也能运行；
- 10 条测试仍全部通过；
- 至少形成 3 条真实反馈；
- 能在 5 分钟内演示“issue → 修改 → 测试 → PR → 合并”。

## AI 使用规则

本周允许 AI 帮忙，但要保留判断权：

- 可以让 AI 解释报错、生成测试候选、检查 README 是否遗漏；
- 不让 AI 一次性重写整个项目；
- 每次接受改动前查看 diff；
- 对每个新增函数，自己能说明输入、输出和异常；
- 对每条测试，自己能说明它保护了哪一项业务承诺。

推荐提问模板：

```text
目标：把现有成本计算器整理成可测试的交付物。
当前文件：
本次只允许修改：
验收标准：
请先说明你准备改什么，不要直接重写整个项目。
完成后列出改动、测试方法和仍存在的风险。
```
